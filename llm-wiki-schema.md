# Software Factory Wiki Schema

A wiki schema for agentic software engineering across multiple projects. Optimized for a developer using Claude Code with NixOS, Scala 3, Kyo, PostgreSQL, and functional programming.

Derived from analysis of two prior wiki designs. See `llm-wiki-for-software-factories.md` for the rationale.

---

## Core Principles

1. **Route before acting.** Resolve scope before reading or writing.
2. **Check ownership before writing.** Never write to human-owned files.
3. **Compliance by declaration.** Projects declare their relationship to norms.
4. **Silence is not compliance.** Missing declarations are drift.
5. **Contradictions are preserved.** Do not auto-resolve.
6. **Normative creates obligations; descriptive creates awareness.**
7. **The agent cannot edit its own rules.** POLICY.md and ownership.md are human-owned.
8. **Fit in context.** The full schema fits in one agent context window.
9. **Promote from evidence.** Local patterns become global only with demonstrated value.
10. **The wiki is not the code.** Link to code; do not duplicate it.

## Routing

Every request is one of: **ingest**, **query**, **edit**, **lint**, **synthesize**, or **meta**.

Determine the target scope before acting:

1. If the request names a project -> scope is `project:<name>`. Read `projects/<name>/CLAUDE.md`.
2. If the request is about a pattern, architecture, decision, capability, or technology -> scope is `tech`. Operate under `tech/`.
3. If ambiguous -> search `tech/index.md` first, then project indices. Synthesize across both. Cite sources from both layers.
4. If the request involves a source document -> source in `sources/raw/`, summary in `sources/summaries/` with `relevant_to:` tags.
5. If still unresolved -> ask exactly one routing question.

**Cross-layer rules:**
- A project ADR referencing a tech page must verify the tech page exists. If absent, create a stub first.
- Tech-layer pages must not mention specific projects in the body. Cross-references go in `used_by:` frontmatter.
- Cross-project syntheses live in `/syntheses/`. Project-scoped syntheses live in `projects/<name>/syntheses/`.

## Ownership

Three classes. Every directory has a default; individual files can override via frontmatter.

| Path glob                     | Default   | Override? | Notes                                          |
|-------------------------------|-----------|-----------|------------------------------------------------|
| `CLAUDE.md`, `*/CLAUDE.md`    | shared    | no        | Human leads; agent proposes edits              |
| `POLICY.md`                   | human     | no        | Agent never edits without instruction          |
| `tech/architecture/**`        | llm       | yes       | Agent owns structure descriptions              |
| `tech/patterns/**`            | llm       | yes       | Agent captures and maintains patterns          |
| `tech/decisions/**`           | shared    | yes       | Human authors intent; agent fills structure    |
| `tech/stack/**`               | llm       | yes       | Agent maintains technology catalog             |
| `tech/capabilities/**`        | llm       | yes       | Agent maps capabilities to implementations     |
| `tech/guides/**`              | llm       | yes       | Agent writes how-to guides                     |
| `tech/glossary.md`            | shared    | no        | Either party defines terms                     |
| `tech/index.md`               | llm       | no        | Generated catalog                              |
| `projects/*/adr/**`           | shared    | yes       | Human authors decisions; agent structures      |
| `projects/*/tickets/**`       | shared    | yes       | Either party creates/updates work              |
| `projects/*/architecture.md`  | shared    | yes       | Collaborative                                  |
| `projects/*/interfaces.md`    | shared    | yes       | Collaborative                                  |
| `projects/*/risk.md`          | shared    | yes       | Collaborative                                  |
| `projects/*/log.md`           | llm       | no        | Append-only. Agent writes; human reads         |
| `projects/*/syntheses/**`     | llm       | yes       | Agent generates analyses                       |
| `projects/*/index.md`         | llm       | no        | Generated                                      |
| `sources/raw/**`              | human     | no        | Immutable after add                            |
| `sources/summaries/**`        | llm       | yes       | Agent summarizes sources                       |
| `syntheses/**`                | llm       | yes       | Agent generates cross-project analyses         |
| `meta/ownership.md`           | human     | no        | Canonical ownership source                     |
| `meta/drift.md`               | llm       | no        | Generated by lint                              |
| `meta/registry.md`            | shared    | no        | Human adds projects; agent updates status      |
| `meta/log.md`                 | llm       | no        | Cross-cutting events                           |
| `tools/**`                    | human     | no        | Executable scripts, human-maintained           |

**Behavior:**
- **human**: agent reads, never writes. Surfaces proposals in conversation.
- **llm**: agent owns. May create, edit, restructure. Human reads but should not hand-edit.
- **shared**: either party edits. Agent edits are flagged in conversation for review.

**Overrides:** When allowed, use frontmatter:
```yaml
ownership: human
ownership_reason: Decision still in draft; human is iterating.
```
`ownership_reason` is mandatory when overriding. Lint enforces this.

## Page Kinds and Compliance

### Kinds

Every page declares a `kind` in frontmatter:

| Kind          | Meaning                                              | Enforcement                    |
|---------------|------------------------------------------------------|--------------------------------|
| `normative`   | A rule, decision, or pattern that creates obligations | Drift checks, compliance       |
| `descriptive` | An observation, fact, or analysis. No obligations     | Freshness, contradiction checks|
| `stub`        | Placeholder. Not enforced until filled in             | Surfaced by lint               |

### Compliance Frontmatter

Every project ADR has a `compliance` block:

```yaml
compliance:
  adopts:
    - tech/decisions/effects-kyo.md
    - tech/patterns/typed-errors.md
  exceptions:
    - page: tech/patterns/immutable-state.md
      rationale: |
        The rendering pipeline uses a mutable frame buffer for performance.
        Immutability is maintained at the domain model level.
      risk: low
  deviations:
    - page: tech/decisions/require-property-tests.md
      rationale: |
        Property test generators for Wayland protocol types are not yet written.
        Unit tests cover the critical paths.
      severity: medium
      mitigated_by: Manual testing of edge cases documented in tests/manual.md
  ignores:
    - page: tech/guides/jvm-tuning.md
      rationale: Scala Native target, not JVM.
```

**Compliance categories (imported from Wiki-1's governance vocabulary):**

| Category    | Meaning                                      | Requirements                  |
|-------------|----------------------------------------------|-------------------------------|
| `adopts`    | Follows this norm as specified               | Target must exist, be normative |
| `exceptions`| Bends a preference with justification        | Rationale + risk assessment    |
| `deviations`| Violates a requirement with mitigation       | Rationale + severity + mitigation |
| `ignores`   | Norm does not apply to this project          | Brief rationale                |

**Rules:**
- `adopts` targets must be normative and not superseded.
- `exceptions` require a non-empty rationale and risk level.
- `deviations` require rationale, severity (low/medium/high), and mitigation.
- `ignores` requires a rationale (can be brief).
- **Silence is not compliance.** Lint flags projects that never address a relevant normative page.

## Page Types

**decision** — An organizational or architectural decision that projects must address.

```yaml
updated: 2026-05-15

  languages: [scala]
  domains: [any]
  excludes: [shell-scripts, nix-modules]
used_by: []                        # maintained by lint
sources: []
supersedes: []
superseded_by: null
---

## Context
## Decision
## Consequences
## Alternatives Considered
## Code Examples
## Links
```

## Normative Tech Page Format

Normative pages under `tech/` declare their scope:

```yaml
applies_to:
  languages: [scala, scala-native]   # which language ecosystems
  domains: [any]                      # which problem domains
  excludes: [shell-scripts]           # explicit exclusions
```

A project is in-scope when its tech stack overlaps with any declared language or domain. In-scope projects must adopt, except, deviate from, or ignore the page in an ADR.

## Capabilities

Capabilities are architectural needs independent of specific technology:

```
persistence          — durable data storage
effects              — effect management and composition
http-api             — HTTP endpoint definition and serving
html-rendering       — server-side HTML generation
authentication       — identity verification
deployment           — getting code into production
configuration        — runtime and build-time settings
observability        — logging, metrics, tracing
build                — compiling and packaging
dev-environment      — reproducible local development
testing              — verification strategy
```

Each capability page describes what the capability means, lists how each project satisfies it, and compares approaches.

## Promotion Flow

Local project patterns can become global knowledge:

```
project log entry
  -> project synthesis ("we keep solving X this way")
  -> cross-project synthesis ("3 projects solve X the same way")
  -> tech pattern (reusable guidance)
  -> tech decision (normative requirement, if warranted)
```

**Promote when:**
- The pattern appears in 2+ projects
- It solves a recurring problem
- Tradeoffs are understood
- It aligns with architectural principles

**Do not promote when:**
- Project-specific
- Insufficient evidence
- Still experimental
- Enforcing it would reduce useful flexibility

**Promotion metadata:**
```yaml
promoted_from:
  - projects/compositor/syntheses/error-boundaries.md
  - projects/webapp/adr/003-typed-errors.md
promotion_reason: Consistent successful use of typed error boundaries across projects
promoted_at: 2026-05-15
```

**Demotion:** A decision can be relaxed to a pattern. A pattern can be deprecated. Record with `status: deprecated` and `superseded_by:`.

## Operations

### Ingest

Input: a source document in `sources/raw/` or a user assertion.

1. Read the source.
2. Determine relevance: which projects, which tech-layer pages.
3. Write summary to `sources/summaries/<slug>.md` with `relevant_to:` tags.
4. For each touched page, propose updates. Apply if ownership allows; surface otherwise.
5. Append to relevant `log.md` files.
6. Update affected `index.md` files. Update `used_by:` lists.

### Query

Input: a question.

1. Route per scope rules.
2. Read relevant index files to identify candidate pages.
3. Read candidates. Synthesize answer with inline citations `[[path/to/page]]`.
4. If the answer reveals a novel insight, propose filing a synthesis. Do not write without confirmation.
5. If the answer reveals a gap, record in the relevant `log.md`: `## [date] gap | <description>`.

### Edit

Input: an instruction to modify a page.

1. Check ownership. Refuse human-owned. Flag shared edits.
2. Make the edit.
3. Run localized lint: frontmatter valid? Links resolve? Compliance block intact?
4. If editing a normative tech page, note that all projects citing it may need review.

### Lint

Input: `lint`, `lint <project>`, or `lint tech`.

Checks:
1. **Ownership** — frontmatter ownership matches defaults or has valid override with reason.
2. **Links** — all wiki links resolve. No dangling references.
3. **Orphans** — pages with zero inbound links (except stubs and newly created pages).
4. **Frontmatter** — required fields present, kind valid, status valid.
5. **Compliance** — project ADRs have compliance blocks. All `adopts:` point to existing normative pages. All `exceptions:` and `deviations:` have rationales.
6. **Drift** — normative pages with in-scope projects that never address them.
7. **Contradictions** — pages making opposing claims. Record, do not resolve.
8. **Staleness** — pages with old `updated:` dates relative to sources or related pages.
9. **Stubs** — surface unfilled stubs.

Output: markdown summary. Write drift findings to `meta/drift.md`. Do not silently rewrite content.

### Synthesize

Input: `synthesize <scope>` where scope is a project, `tech`, or `cross-project`.

1. Read all pages in scope.
2. Identify patterns, repeated problems, drift, technology evolution, promotion candidates.
3. Write synthesis to appropriate location (project syntheses/ or root syntheses/).
4. Cite all source pages.
5. Mark confidence level.
6. Update logs and indices.

### Promote

Input: `promote <project-pattern> to tech/<target>`.

1. Verify the pattern exists and has evidence.
2. Check for similar existing tech pages.
3. Create or update the tech page with `promoted_from:` metadata.
4. Update the originating project's synthesis to note the promotion.
5. Log the promotion.

### Meta

Routing, ownership, or policy changes. Always shared or human. Never unilateral.

```markdown
# <project-name> — Wiki Schema

One paragraph: what this project is, its stage, what the wiki captures.

## Stack

- Language: Scala 3 / Scala Native
- Effects: Kyo
- Database: PostgreSQL / SQLite
- Build: Mill / Nix
- Platform: NixOS

Project-specific tags (cross-project search uses `relevant_to` and

- `layer:` domain | application | infrastructure | presentation
- `phase:` design | prototype | stable

- Filename: `adr/NNNN-kebab-title.md` (monotonic)

Document any deviation from root schema here with rationale.
```

## Linking Conventions

- Use wiki links for internal references: `[[tech/decisions/effects-kyo]]`
- Use relative paths from wiki root
- Use normal markdown links for external URLs
- Every page should link to at least one other page
- When mentioning a concept or technology that has a page, link it

## Naming Conventions

- All lowercase, kebab-case: `typed-error-boundaries.md`
- ADRs: `NNNN-kebab-title.md` (project-local monotonic numbering)
- Tickets: `NNNN-kebab-title.md`
- Syntheses: descriptive names, optionally date-prefixed for periodic analyses
- Log entries: date-prefixed within the log file

## Citations

Every claim cites its source as `[[path/to/page]]`. Claims from raw sources cite the summary, not the raw file. The wiki is a compiled view of authorities, never the original authority.

---

## What This Schema Deliberately Does Not Do

- **Does not enforce SHA-256 hashes.** File paths + timestamps are sufficient for provenance at this scale. Hashes require external tooling the LLM cannot maintain.
- **Does not record model runs.** Session logs in `log.md` capture what happened. Formal run records are bureaucratic overhead for interactive development.
- **Does not enforce a tag taxonomy.** Each project defines its own tags. Cross-project discovery uses `relevant_to`, `compliance`, and `capabilities` frontmatter.
- **Does not version pages.** Use git. The wiki is in a git repository.
- **Does not embed vector search.** Index files + grep suffice for hundreds of pages.
- **Does not auto-resolve contradictions.** Contradictions are information.
- **Does not require Obsidian.** The wiki is terminal-first. Obsidian compatibility is a bonus, not a requirement.
- **Does not lock technology choices.** Coherence means documented, justified choices — not uniformity.
