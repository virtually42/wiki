## Goal

`/p/hg/dependency-manager/README.md` carries a step-by-step
"Adopting dm in a downstream repo" section so future consumer
migrations (or new repos joining the `/p/hg/` cohort) can follow a
script rather than re-discover the rules from log entries.

Critical content the section **must** include:

1. The Mill 1.x `deps/package.mill` anchor requirement (discovered
   during slm migration on 2026-05-29; not documented in upstream
   Mill llm-wiki under `patterns/build-file-structure.md`). One line:
   `package build.deps`. Without it, Mill silently ignores the
   generated `Dependencies.mill`.
2. The `projects.yml` registration step — a new consumer must be
   added to dm's `projects.yml` with its absolute path and the list
   of library handles it consumes.
3. The kebab → camel naming rule (e.g. `munit-scalacheck` →
   `Deps.munitScalacheck`, `os-lib` → `Deps.osLib`,
   `sourceline-manager` → `Deps.sourcelineManager`). This is
   load-bearing — callers must use the catalog form.
4. The bootstrap order: first `dm extract` (catalog learns about
   the new project), then add `deps/package.mill`, then rewrite
   `build.mill` mvnDeps, then `dm verify --project=<name>`.
5. The verify gate workflow: per-CI-job `bin/dm verify`, exit 1
   means drift → run `dm regen` to fix.
6. The boundary: dm catalogs **library coordinates only**. Platform
   versions (Scala, Scala.js, Scala Native) stay in the consumer's
   own `object V` or equivalent.

## Notes

The Mill upstream `llm-wiki` page
`mill/llm-wiki/patterns/build-file-structure.md` documents
`package.mill` for *defining modules* but does not flag the
helper-discovery side effect. A separate (deferred, low-priority)
follow-up could PR that upstream — but for this ticket, documenting
in dm's README + the wiki decision page is sufficient.

**Template prose** (not normative; the author may revise):

```markdown
## Adopting dm in a downstream repo

To register a new project as a dm consumer:

### 1. Bootstrap the catalog with the new project

```bash
cd /p/hg/dependency-manager
bin/dm extract --force /p/hg/<existing-projects>... /p/hg/<new-project>
# Catalog now knows about <new-project>'s dependencies.
git diff deps/  # review the additions
```

### 2. Add the Mill 1.x discovery anchor

dm regenerates `deps/Dependencies.mill` into the new project, but
Mill 1.x ignores sibling `.mill` files in folders that lack a
`package.mill`. Hand-author one:

    cd /p/hg/<new-project>
    mkdir -p deps && cat > deps/package.mill <<'EOF'
    // Anchors the `deps/` folder so Mill 1.x discovers sibling `*.mill`
    // helpers (notably `Dependencies.mill`, generated by `dm regen`).
    package build.deps
    EOF

### 3. Generate the dependencies file

```bash
cd /p/hg/dependency-manager
bin/dm regen --project=<new-project>
# Produces /p/hg/<new-project>/deps/Dependencies.mill
```

### 4. Rewrite `build.mill` mvnDeps

Replace every `mvn"…::${V.x}"` with `build.deps.Deps.<handle>`.
The handle is the kebab name camel-cased (`os-lib` → `osLib`,
`munit-scalacheck` → `munitScalacheck`).

Keep platform versions (Scala, ScalaJS, ScalaNative) in `object V`
— those are not catalog-managed.

### 5. Verify

```bash
cd /p/hg/<new-project> && mill __.compile && mill __.test
cd /p/hg/dependency-manager && bin/dm verify --project=<new-project>
```

Both should be green. The catalog is now the source of truth for
this project's external Maven dependencies.
```
