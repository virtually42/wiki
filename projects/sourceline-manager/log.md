## [2026-05-29] implement | build.mill migrated to dm-managed Deps catalog

First downstream consumer of the dm catalog. `build.mill` now
references `build.deps.Deps.munit` and `build.deps.Deps.munitScalacheck`
from the auto-generated `deps/Dependencies.mill` instead of inline
`V.munit` / `V.munitScalaCheck` strings.

### Diff in summary

- Removed `V.munit` (`"1.0.3"`) and `V.munitScalaCheck` (`"1.0.0"`)
  from `object V`. Replaced with a comment pointer.
- `SlmTestSources.mvnDeps` now `Seq(build.deps.Deps.munit,
  build.deps.Deps.munitScalacheck)` — direct references, no `mvn"…"`
  template string in `build.mill` for these two artifacts.
- Added `deps/package.mill` (one line: `package build.deps`) as the
  Mill 1.x discovery anchor. Without it, Mill ignores sibling `.mill`
  files in folders that lack a `package.mill` or `build.mill`.

### Naming note

Old code used `V.munitScalaCheck` (capital C). The catalog handle
is `munit-scalacheck`, which dm camel-cases to `munitScalacheck`
(lowercase c). Build.mill now uses the catalog form — divergence
from the local convention is forced by adoption of the catalog
naming rule.

### Verification

```
$ mill __.compile                  →  338/338 SUCCESS
$ mill slm.jvm[3.8.3].test         →  140/140 tests green
$ bin/dm verify --project=sourceline-manager   →  OK
```

`mvn"org.scalameta::munit::1.0.3"` and `…::munit-scalacheck::1.0.0`
remain on the test classpath at runtime — the `Deps.*` references
resolve to the same `mvn` literals via Mill's eager evaluation.

### Architectural status

`projects/sourceline-manager/adr/0002-deviate-deps-single-file` is
**partially expired** — its expiry condition "library gains a second
external library dependency" can be read as triggered (munit and
munit-scalacheck are separate catalog entries even though
munit-family), and the deviation's premise ("no `deps/Dependencies.mill`
file") no longer holds: `deps/Dependencies.mill` exists (auto-generated)
and `build.mill` consumes it.

What does *not* conform yet: the `object Platform` half of the
canonical [[tech/decisions/deps-single-file]] shape. slm's
`object V` still holds `scalaVersions`, `scalaJS`, and `scalaNative`
— dm's catalog has no platform-version surface (intentional: those
aren't Maven coordinates and don't fit Renovate's manager model).

Net: the *library coordinates* now conform via dm; the *platform
versions* deviate. A clean follow-up would be either:

- Revise ADR-0002 to a narrower deviation ("inline platform versions
  only"), or
- Write ADR-0003 adopting deps-single-file with a documented
  platform-version exception.

Deferred — this slice is the implementation; the normative shift is
a separate decision. Flagging here so the next lint pass surfaces
it on `meta/drift.md`.

### Why slm got picked first

- Two libraries — smallest consumer surface.
- Both libraries are test-only — no risk to production publishing.
- Both are munit family — `dm extract` had already de-duplicated
  them across toolbox / slm / safetensors so the catalog version
  was already authoritative.

Migrations of toolbox/build.mill (10 libraries, mixed runtime + test)
and safetensors-scala/build.mill (3 libraries including a pinned
`scodec`) are the obvious next slices — deferred to separate
sessions because the surface is larger.

## [2026-05-29] implement | MonoidLawsSuite[A] — closes DRIFT-015h, raises tdd-rhythm to confidence: high

recommended. Three new test files in
`/p/hg/sourceline-manager/slm/test/src/slm/` (shared across JVM /
Scala.js / Scala Native):

  `forAll`.

## [2026-05-29] implement | SourceLine primitives + StringUtils-composition spec + primitive-laws spec — test-economics raised to confidence: high

Extended `SourceLine` with a minimal orthogonal primitive set
(slicing / search / predicates / pattern / joining — 16 methods),
then proved both *expressivity sufficiency* and *algebraic
contract* in two new test files.

Files added under `/p/hg/sourceline-manager/slm/`:

- `src/slm/SourceLine.scala` — 16 new primitive methods grouped
  into five families: slicing (`take`, `drop`, `splitAt`,
  `takeWhile`, `dropWhile`), search (`indexWhere`,
  `lastIndexWhere`, `indexOfSlice`), predicates (`exists`,
  `forall`, `count`, `find`), pattern (`startsWith`, `endsWith`,
  `contains`), joining (`intersperse`). Each is a one-line wrap
  over the underlying `Vector[Token]`.
- `test/src/slm/StringUtilsCompositionSpec.scala` — 30 tests.
  Derives 23 Apache Commons `StringUtils`-equivalent functions
  (`left`, `right`, `mid`, `substring`, `trim`, `strip`, `chop`,
  `chomp`, `repeat`, `wrap`, `padLeft`, `padRight`, `center`,
  `countMatches`, `countMatchesSlice`, `containsAny`,
  `defaultIfEmpty`, `appendIfMissing`, `prependIfMissing`,
  `replaceAll`, `replaceSlice`, `abbreviate`, `join`, plus
  `isBlank` and three primitive sanity checks) as local `def`s
  composing only existing operators. The primitive set is shown
  *sufficient*; no methods added to `SourceLine` itself.
- `test/src/slm/SourceLinePrimitivesLawsSpec.scala` — 46
  `forAll`-quantified ScalaCheck properties grouped by primitive
  family. Slicing duality (`take(n) ++ drop(n) == self`), `take`
  monotone-idempotence, `drop` composition, length invariants,
  predicate-slicing saturation, search-result correctness, De
  Morgan (`forall(p) == !exists(!p)`), partition law, find /
  filter equivalence, pattern-match biconditionals
  (`startsWith(p) ⇔ take(p.length) == p`), intersperse length
  (`2n − 1`), and closure laws for the existing operators
  (`reverse` involution + anti-distributivity, `map(identity)`,
  `filter` constant predicates).

Build / test results:

- No build change required — `org.scalameta::munit-scalacheck` was
  already on the test classpath from the prior MonoidLawsSuite
  landing.
- `mill 'slm.jvm[3.8.3].test'` → 227/227 green (up from 140/140:
  +30 composition cases + 46 primitive laws + 11 expanded
  existing tests; ScalaCheck default 100 samples per property).

Wiki effects:

  gains a §"Status Update — 2026-05-29 (post-primitives +
  StringUtils composition)" recording the new evidence and its
  effects on each cited pattern.
- [[tech/patterns/test-economics]] **promoted**: `status: draft`
  → `accepted`, `confidence: medium` → `high`. The FP-stack
  amortisation case is now realised at two layers (monoid + 16
  primitives certifying 23 derived functions). The §"FP-stack

What this proves that the monoid laws alone did not: the
algebraic-contract claim now covers the *entire* operator
catalogue, not the (`empty`, `++`) layer only. The composition
spec is the *demonstration* of sufficiency; the laws spec is the
*maintenance guarantee* against future refactors. Together they
are the answer to the user-side question "did we actually prove
FP is more maintainable than imperative `StringUtils`?" — the
expressivity result (composition spec) plus the
refactor-resistance result (laws spec) is the proof; without the
laws spec the demonstration is only a static snapshot.
