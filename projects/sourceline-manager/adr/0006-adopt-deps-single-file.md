## Context

[[tech/decisions/deps-single-file]] (accepted 2026-05-24, global
scope) requires Scala projects to declare dependencies in a
single `deps/Dependencies.mill` file with inline `mvn"…"`
coordinates.

Up to 2026-05-29, `sourceline-manager` deviated:
`build.mill`'s `object V` declared `munit` and
`munit-scalacheck` versions inline, no `deps/Dependencies.mill`
file existed. The deviation was recorded in
[[projects/sourceline-manager/adr/0002-deviate-deps-single-file]]
with an expiry condition: "embedded into the monorepo" or
"the library gains a second external library dependency".

The second condition partially held (two external libs:
`munit`, `munit-scalacheck`), but the file-extraction trade-off
was changed more fundamentally by the
[[projects/dependency-manager/index]] project. dm produces a
generated `deps/Dependencies.mill` per consumer from a central
TOML catalog, sidestepping the monorepo-embedding precondition.

On 2026-05-29, `sourceline-manager` migrated to consume
`build.deps.Deps.munit` and `build.deps.Deps.munitScalacheck`
from the dm-generated file (see
[[projects/sourceline-manager/log]] § "Consumer-side catalog
loop closed (slm migrated to Deps)" / the dm log under
[[projects/dependency-manager/log]]).

This ADR records the resulting conformance with
[[tech/decisions/deps-single-file]], with a single narrow
exception for platform versions.

## Decision

Adopt [[tech/decisions/deps-single-file]] for **external Maven
library coordinates**. These now live in `deps/Dependencies.mill`,
auto-generated by `dm regen` from the catalog at
`/p/hg/dependency-manager/deps/`.

Continue to inline **platform versions** (`scalaVersions`,
`scalaJS`, `scalaNative`) and project-internal metadata
(`organization`, `artifact`, `projectVersion`) in `build.mill`'s
`object V`. dm intentionally does not manage platform versions
(Renovate's Maven model does not cover them; conflating shapes
is wrong) — see
[[projects/dependency-manager/designs/dm-architecture]] for the
deferral rationale.

The Mill 1.x discovery anchor `deps/package.mill` (one line:
`package build.deps`) is required for Mill to discover the
generated `Dependencies.mill`. This is a hand-authored
per-consumer setup file, documented in
[[tech/decisions/deps-single-file]] §"Mill 1.x discovery
pre-requisite" and the
[adopting-dm README section](https://github.com/tigidar/dependency-manager#adopting-dm-in-a-downstream-repo)
(in-tree).

## Consequences

- `deps-single-file`'s automation goal is met for external
  Maven deps: Renovate parses the central catalog;
  `dm regen` rewrites this project's `Dependencies.mill`;
  Mill picks up the change at the next compile.
- Cross-project version drift on external deps is eliminated
  by construction — the catalog is the single source of truth.
- A narrow exception remains for platform versions; documented
  in the `compliance.exceptions` block above. Severity is
  `low` because the exception is principled (Maven model
  boundary) rather than incidental.
- `meta/drift.md` should now flag this project as **adopting**
  `deps-single-file` (with the platform-versions exception),
  not deviating.

## Alternatives Considered

- **Adopt unconditionally including `object Platform`.**
  Rejected: would require either inventing a new YAML/TOML
  shape for platform versions (and a per-shape Renovate manager
  to bump them), or hand-rolling the bump path. dm explicitly
  defers this; cloning the rejection of premature optimisation
  is the right call.
- **Keep the original deviation.** Rejected: the migration
  closed the deviation's core concern (extraction had no
  payoff while standalone). Honest re-classification is
  better than ADR rot.
- **Single rewrite of ADR-0002.** Rejected: the supersession
  is cleaner — the previous deviation's reasoning chain
  ("standalone, embedding will resolve") was specific to the
  monorepo timeline. The current adoption rests on the dm
  abstraction instead, which is a different mechanism. Two
  ADRs keep the reasoning history legible.
